# PC Advisor BG — Project Operating System Design Specification

**Date:** 2026-08-26  
**Status:** Approved design captured for final owner review  
**Design path:** Architectural  
**Implementation status:** Not started  
**Authoritative scope:** Pre-coding project operating system only

## 1. Purpose

This specification defines how PC Advisor BG will be owned, governed, developed, reviewed, deployed, operated, backed up, and recovered **before product coding begins**.

The purpose is to enable a highly autonomous coding agent while preserving strict owner control over money, production, destructive actions, business scope, legal/commercial decisions, and account ownership.

> **The owner approves the destination and boundaries. The agent owns the technical path to reach that destination safely.**

This document does **not** authorize product implementation. Product coding may begin only after the Project Operating System passes the Ready-to-Code Gate defined here.

## 2. Non-Negotiable Principles

1. **Superpowers is the only software-development methodology.** Operational tools may provide access to services, documentation, browsers, CI, databases, or observability, but they do not replace the Superpowers workflow.
2. **No implementation before approved design and plan.** Architectural work follows `brainstorming → approved design → written spec → owner review → writing-plans → execution`.
3. **Autonomy is broad inside a narrow approved boundary.** The owner approves a Phase Brief as a package. The agent does not request repetitive micro-authorizations for normal diagnostics, tests, repairs, commits, PRs, staging work, or green auto-merges that remain within that approved phase.
4. **Production is a separate security boundary.** The normal coding agent must not possess the credentials required to mutate the production database or deploy production.
5. **Money requires explicit owner approval.** The target is €0 mandatory recurring infrastructure cost at launch wherever reasonably safe. No agent may activate a paid plan, paid add-on, non-zero recurring resource, or automatic paid upgrade without owner approval.
6. **Discovery is not authorization.** Finding a better idea, refactor, new service, dependency upgrade, feature, or architecture during a task does not authorize implementing it.
7. **The repository is public source, not open source.** Source is publicly viewable, but no open-source license is granted. External contributions are not part of V1.
8. **Everything committed must be safe to publish on the internet.** Secrets, credentials, owner email, sensitive identifiers, backups, recovery material, and private operational data do not belong in Git.
9. **Owner operations should be owner-friendly.** Routine post-launch business operations should be available from the Admin Control Center when appropriate, without requiring SQL, source edits, `.env` changes, or GitHub operations.
10. **Evidence before completion claims.** “Done” requires verification, not confidence.

A separate Supabase account using the project Proton identity is created.

- `pc-advisor-production`

- PostgreSQL
- Supabase Auth for owner Admin login
- local Supabase CLI

Do not enable public signup, Realtime, Storage, Edge Functions, branching, or extra Supabase products unless a later approved phase proves a requirement.

### 4.5 Cloudflare

A separate Cloudflare account using the project Proton identity is created to reduce blast radius from unrelated projects.

Cloudflare is the hosting platform.

The system uses:

- separate staging and production application targets
- Cloudflare Access for protected staging
- Cloudflare Web Analytics where appropriate
- private R2 for approved backup storage
- scoped API tokens, never a Global API Key

The exact currently supported stable Next.js-to-Cloudflare deployment path is verified during setup and pinned in project documentation. The agent may make that bounded technical selection only if it meets all approved architecture constraints. A second hosting provider requires owner approval.

### 4.6 Domain

No domain purchase is required during initial setup.

The final name/domain is chosen before the first public staging/SEO phase.

Any non-zero domain cost requires owner approval.

## 6. AGENTS.md Contract

`AGENTS.md` is the agent constitution and router, not a project encyclopedia.

Target size: roughly 200–350 structured lines.

It defines or links to:

- product purpose
- mandatory Superpowers methodology
- active Phase Brief requirement
- autonomy boundaries
- Production boundary
- money boundary
- tool policy
- stop conditions
- verification requirement
- reporting standard
- authoritative documentation routing

### 6.1 No work without active Phase Brief

Before changing code or infrastructure, the agent identifies the approved active Phase Brief.

Old plans, tasks, chat history, future-roadmap items, comments, or provider dashboards are not authorization.

### 6.2 Start-of-task preflight

The agent verifies:

- correct repository
- branch
- exact starting SHA
- working tree state
- required tools
- active phase
- target environment
- safe required credentials

Hosted target identity is proven rather than assumed.

### 6.3 Superpowers workflow

For feature/behavior work:

`design/spec → plan → TDD → independent review → verification`

Architectural work obeys the hard design approval gate.

### 6.4 Task granularity

Work is divided into small independently valid tasks.

Every merged task leaves `main` working.

Incomplete large features remain inaccessible or safely feature-gated.

### 6.5 TDD

Where behavior is reasonably testable:

- prove missing/broken behavior
- implement minimal correction
- prove green behavior
- refactor only as justified by the task

Tests protect behavior rather than merely satisfying process.

### 6.6 Review model

Every normal task receives:

1. fresh implementer
2. independent Superpowers spec/quality review

Risk-triggered specialist review:

- DB/RLS/Auth/Admin → security + data integrity
- secrets/Cloudflare/GitHub/deploy → infrastructure/security
- recommendation engine → correctness/invariant
- public UI → real browser + accessibility
- SEO/content → source/copyright

Low-risk text/CSS work does not receive pointless specialist review.

Every phase ends with a broad independent whole-phase review.

### 6.7 Repair autonomy

Failed test, build, CI, staging defect, browser race, or reproducible engineering defect is normal engineering work.

If repair remains inside approved scope, the agent diagnoses, repairs, reviews, and reruns without owner permission.

### 6.8 Anti-loop rule

Do not repeat an identical failed action without a concrete reason.

A retry needs:

- a repair
- a new diagnostic hypothesis
- verified recovery of a transient dependency
- a changed precondition

Repeated identical failure requires diagnosis, not repeated execution.

### 6.9 Scope control

> **Discovery is not authorization.**

Out-of-scope findings go to the private Project Parking Lot and do not modify the active plan.

## 7. Autonomy and Stop Conditions

### 7.1 Allowed without new owner approval inside an approved Phase Brief

The agent may:

- create task branches
- implement via TDD
- commit/push
- open/update PRs
- run CI
- diagnose/repair CI failures
- run reviews
- use approved Local resources
- use approved Staging resources
- perform safe non-destructive Staging migrations
- deploy to Staging
- run browser/E2E verification
- repeat diagnostics with concrete reason
- auto-merge fully green tasks
- proceed to the next approved task in the phase
- update the private Project and recovery ledger

### 7.2 Mandatory owner approval

Stop before:

- activating/increasing paid spend
- Production deployment
- Production migration
- destructive Production action
- destructive external action outside authorized scope
- use of real user data beyond explicitly approved operational access
- legal decision
- commercial decision
- affiliate/commercial policy change
- licensing change
- repository visibility change
- architecture expansion beyond the Phase Brief
- a new service/provider that changes approved architecture
- a genuine unresolved blocker requiring owner/business choice

### 7.3 Operational states

**REPAIR** — technical problem inside approved scope; continue autonomously.

**BLOCKED** — proven dependency/boundary prevents progress; preserve state and report.

**OWNER DECISION REQUIRED** — business, cost, Production, destructive, legal, commercial, or scope decision is needed.

The agent presents a concrete decision, not “What should I do?”

## 12. Environment Architecture

```text
Windows / Local
      ↓
GitHub / CI
      ↓
Staging
      ↓
Production
```

They do not share unrestricted credentials.

### 12.1 Local

Contains application code, local Supabase/Postgres, synthetic data, and local environment values.

No Production DB credential is needed to run locally.

Local DB state is reproducible from migrations and approved seeds/fixtures.

### 12.2 GitHub / CI

Normal CI may have Staging-scoped secrets required for approved automation.

Normal CI must not have:

- Production DB admin credential
- Production Supabase service-role/secret credential
- Production migration credential
- normal Production Cloudflare deployment token
- Bitwarden credentials
- owner recovery credentials
- Production backup reader
- backup encryption master material

### 12.3 Staging

Staging is the autonomous hosted verification environment.

It has separate Supabase project/database/Auth identities/Cloudflare target/URL/credentials and no real Production data.

It is protected with Cloudflare Access and `noindex`.

Browser automation uses a machine/service method, not the owner’s personal login.

### 12.4 Production

Production is locked.

The normal coding agent does not receive:

- Production Supabase MCP
- Production DB admin password
- Production migration credential
- normal Production Cloudflare deployment token

This is enforced by credential absence, not policy alone.

### 12.5 Hosted target preflight

Before hosted migration/deployment, tooling verifies as applicable:

- Git repository
- branch
- exact SHA
- declared environment
- Supabase project ref
- Cloudflare target

Contradictory target identity fails closed.

## 13. Supabase Security Model

V1 Supabase Auth serves the single owner Admin account.

Rules:

- public registration disabled
- successful login alone does not imply authorization
- authenticated identity must match explicitly authorized owner
- RLS where exposed tables require it
- authorization does not rely on mutable user-controlled metadata
- service-role/secret credentials never reach browser code
- Production app avoids service-role credentials by default
- adding Production service-role dependency requires approved requirement + security review

Production MCP is not configured.

Staging tooling is project-scoped and limited to approved capabilities.

## 14. Cloudflare Security Model

Separate Staging and Production application targets.

**Staging**
- deployable by approved CI/agent credential
- protected by Cloudflare Access
- `noindex`
- usable for browser verification

**Production**
- no normal agent deployment token
- release requires owner approval
- Production credential remains owner-controlled

Use scoped API tokens, never a Global API Key.

Provider/adapter choices are verified against current official support during setup and pinned once selected.

## 15. Secret Policy

The public repo uses symbolic names, never real values, e.g.:

- `PROJECT_OWNER_EMAIL`
- `STAGING_SUPABASE_PROJECT_REF`
- `PRODUCTION_SUPABASE_PROJECT_REF`
- `CLOUDFLARE_ACCOUNT_ID`

`SECRETS.md` documents purpose, storage location, authorized consumer, and rotation expectations — never actual values.

Base CI includes secret/security scanning.

If a secret may have leaked:

`revoke → replace → determine exposure → verify → document`

Public Git history is treated as publicly obtainable.

## 16. Production Release Model

Merging `main` does **not** deploy Production.

`main` means a verified candidate deployed to Staging.

Before Production, owner receives:

- exact SHA
- what changes
- Staging verification
- DB migration summary
- data risk
- required backup status
- rollback procedure
- known limitations

Production begins only after explicit owner approval and promotes the exact verified candidate.

## 17. Backup and Recovery

### 17.1 Admin Publish Snapshot

Purpose: routine recovery of owner-managed catalog/content/config.

Triggered only by successful Publish, not draft save.

Flow:

`Publish → validate → save/audit → version snapshot → encrypted private R2 storage → health status`

Production runtime uses approved private R2 binding instead of exposing a general R2 API credential to the coding agent.

### 17.2 Full Release Backup

Required before every Production release.

Flow:

`Production DB → read-only backup credential → logical dump → encryption → private R2 → integrity verification`

Production backup reader and owner recovery material do not live in normal agent/GitHub CI.

### 17.3 Retention

Keep:

- latest **30** successful Admin Publish snapshots
- latest **10** successful full release backups

Old backups may be removed only after a newer required backup is validated.

### 17.4 Restore rehearsal

Prove restore:

- before public launch
- after every significant DB/schema change

Restore into a temporary isolated local PostgreSQL/Docker environment; verify archive, schema, key data, and relevant application compatibility; then destroy temporary environment.

Production data is not copied into permanent Staging.

### 17.5 Backup health

Admin Site Health exposes last successful snapshot, relevant full backup state, last restore verification, and clear warnings.

## 26. Pre-Coding Setup Phases

### Phase 0 — Project Operating System Specification

Deliver:
- approved architecture
- written design spec
- self-review
- owner review
- Superpowers implementation/setup plan

No account setup, repository mutation, or product coding before this gate.

### Phase 1 — Owner Foundation

Owner-guided setup of Proton identity, Bitwarden project structure, GitHub Organization, Cloudflare account, Supabase account/Organization, and Staging/Production Supabase projects.

**Gate:** owner controls accounts/recovery; agent has no master credentials.

### Phase 2 — Repository & Local Foundation

Create/configure public repo, rights notice, contribution policy, Issues/Discussions off, private Project, protected `main`, PR-only workflow, local Windows preflight, runtime/package pinning, and one official work directory.

**Gate:** clean checkout is reproducible and repo contains no secrets.

### Phase 3 — Project Operating System Installation

Create approved layered docs/governance and phase/task structures.

**Gate:** fresh agent without chat history can correctly explain authority, boundaries, environments, and stop conditions from repo docs.

### Phase 4 — Tool & Permission Wiring

Wire only the minimal toolset and verify both allowed permissions and forbidden Production capabilities.

**Gate:** allowed operations work; forbidden Production operations are unavailable.

### Phase 5 — Environment Skeleton & Security Proof

Create reproducible Local, protected Staging skeleton, locked Production skeleton/config, private R2 backup storage, environment preflight, fail-closed target checks, and secret scanning.

No product features.

**Gate:** deliberate attempt to route normal Staging workflow toward Production fails safely.

### Phase 6 — CI, Review & Release Conveyor

Prove:

`branch → TDD/review → PR → CI → auto-merge → Staging deploy`

using a trivial reversible test change, not a product feature.

Verify merge does not deploy Production.

**Gate:** green workflow reaches Staging while Production remains untouched.

### Phase 7 — Backup & Recovery Rehearsal

With synthetic data test admin snapshot, R2 write, integrity, full logical backup, encryption, isolated local restore, validation, cleanup, and retention behavior.

**Gate:** both backup existence and restore capability are proven.

### Phase 8 — Owner/Agent Dry Run

Give a fresh agent a bounded mock Phase Brief.

It must recover rules, run branch/TDD/review/PR, repair without micro-authorization, auto-merge only when green, reach Staging, and report clearly in Bulgarian.

Simulate stop scenarios:

- paid resource required
- Production mutation requested
- attractive idea outside scope

**Gate:** agent continues normal engineering autonomously but stops correctly at owner boundaries.

## 27. Ready-to-Code Gate

Product coding is forbidden until all are proven.

### Ownership
Owner controls Proton, Bitwarden, GitHub Organization, Supabase, Cloudflare.

### Cost
Mandatory recurring infrastructure cost is €0 under the verified provider configuration. No automatic paid upgrade is agent-authorized. If current provider limits make €0 unsafe/impossible, stop for owner decision.

### Isolation
Agent has Local + approved Staging capability and lacks normal Production DB mutation/deployment credentials.

### Git/development
Protected `main`, PR-only flow, required CI, reviews, green auto-merge, private Project tracking, fresh-session recovery.

### Staging
